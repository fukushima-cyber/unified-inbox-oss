# 資格情報の保管と配布

作成者が利用者のAPI資格情報を預からない条件は、**各利用者が自分のPCまたはサーバーで受信箱を運用し、DB・マスター鍵・OAuth設定・Botのブラウザログインを自分で管理すること**。コードをGitHubで配布するだけなら、作成者へ資格情報を渡す必要はない。各人は自分のPCで `./setup.sh`、公開サーバーでは `./setup.sh 自分のメールアドレス 自分のドメイン` を実行する。

| 情報 | 置き場 | 作成者が共通サーバーを運用した場合 |
|---|---|---|
| Slack・Chatwork・TeamsのAPIトークン | 受信箱DBの暗号文。鍵はそのホストの `secrets/inbox_master_key` | ホストと鍵を持つ作成者は復号できる |
| TeamsのOAuth更新トークン | 本人の受信箱DBの暗号文 | 共通サーバーの運営者は復号できる |
| GmailのOAuth更新トークンとデスクトップOAuth設定 | 本人端末の `secrets/gmail-agent.json` | トークン自体は共通サーバーへ送らないが、サーバー側の送信要求を本人端末が実行し得る |
| LINE・Messengerのブラウザログイン | 本人のGrok Bot環境 | Cookie等は受信箱に渡さないが、サーバー側の送信要求をBotが実行し得る |
| 会話本文・返信本文 | 受信箱DBの暗号文 | ホストと鍵を持つ作成者は復号できる |

暗号化保存だけではサーバー運営者からの秘匿にならない。Gmailのトークンだけを本人端末へ分けても、共通サーバーの運営者には会話本文と送信要求を管理する権限が残る。このため、この配布方法では共通サーバーを作成者が提供しない。現行の `compose.yaml` を第三者に共用させる場合は「APIを預からない」と説明しない。

新しい `setup.sh` は所有者メールアドレスを記録する。別メールアドレスへの初回設定を拒否し、既存DBに他人の利用者がいる場合は個人用インスタンスとして起動しない。旧版の共有DBを自動分割しない。各人への配布は別のチェックアウト、DB、鍵、ドメインで行う。

本人のPCでも運用できる。`./setup.sh` はループバックの受信箱をログインなしで起動する。Gmailエージェント、Slack・Chatwork・Teamsの定期照合は公開ドメインなしで動く。WebhookとRemote HTTPS MCPには外部から到達できるHTTPS URLが別途必要。PCの電源やスリープ状態が同期の継続性を左右する。公開ドメイン付きの `setup.sh` はDockerと公開80/443番ポートを使うため、PC上で実行する場合もネットワーク設定が必要。

実装の限界として、本人が管理するサーバーの管理者、バックアップ保管先、端末マルウェア、OAuth提供元から情報を完全に秘匿するものではない。Gmailエージェントは取得した本文を本人の受信箱へ転送するため、その受信箱のホストも本人が管理する必要がある。
