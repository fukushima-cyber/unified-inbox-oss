# 本人所有サーバーでの試験運用

作成者が資格情報を預からない配布では、利用者がそれぞれ自分のサーバーとドメインを管理する。`setup.sh` が `INBOX_OWNER_EMAIL` を設定した新規インスタンスは、その本人だけが有効化できる。`compose.yaml` はNode.jsアプリとCaddyを起動し、Caddyが公開HTTPSを担当する。実サーバーでのデプロイ、実サービスの連携、復旧訓練は未実施。

## 初回起動

1. 公開ドメインをサーバーのIPに向け、外部からTCP 80/443を通す。Docker Compose、OpenSSL、curlを利用できるLinuxサーバーに、このリポジトリを配置する。
2. リポジトリ内で次の1コマンドを実行する。公開構成ではメールアドレスとドメインを両方指定する。ドメインに `https://` は付けない。

   ```sh
   ./setup.sh you@example.com inbox.example.com
   ```

   コマンドは `.env` にドメインと所有者、`secrets/inbox_master_key` に鍵を初回のみ保存し、コンテナと公開HTTPSの疎通を確認してから所有者の招待コードを発行する。HTTPS確認が失敗した場合、DNS、80/443の到達性、`docker compose logs` を確認して再実行する。再実行で既存鍵とDBは上書きされない。鍵を失った場合は元の鍵を復元する。別ドメインへ変更する場合は `.env` を手動で更新し、同じ値を指定して再実行する。
3. 招待コードは48時間有効。本人は公開URLで初回設定し、自分の連携を登録する。LINE・Messengerは本人専用Grok Bot、Gmailは本人端末のエージェントを使う。各サービスの権限設定と実接続の確認が必要。

別の利用者は自分のサーバーに別インスタンスを用意する。旧版の `.env` に `INBOX_OWNER_EMAIL` がない共有構成は、この個人用セットアップへ自動移行しない。旧データを持つ場合はバックアップを取り、利用者ごとにデータと資格情報を分けて移行する設計を先に行う。

## バックアップと復旧

稼働中のSQLiteファイルを直接コピーしない。次のコマンドはSQLiteのバックアップAPIを使用し、整合性を確認した別ファイルを作る。既存ファイルは上書きしない。

```sh
docker compose exec app node scripts/backup.mjs /backups/inbox-YYYYMMDD-HHMM.sqlite
```

`/backups` は同一サーバー内のDocker volumeであり、それだけでは障害対策にならない。バックアップと `secrets/inbox_master_key` を別々に、暗号化した外部保管先へコピーする。保存期間と削除は運用側で定める。復旧訓練ではサービスを停止してからDBを戻し、同じマスター鍵で起動して招待・既存会話・返信状態を確認する。復旧直後に未確定の返信を自動で再送しない。

## 運用上の限界

- DBとジョブは単一プロセス前提。アプリを複数レプリカで同じSQLiteへ接続しない。
- 保存上限は利用者ごとにメッセージ1万件、受信イベント2万件、返信要求1万件。上限を超えると新規受信・返信が停止し、連携欄に受信エラーを表示する。自動削除はしない。復旧手順と保持期間を決めるまで長期運用しない。
- Teamsのアクセストークンは自動更新されない。SlackもOAuth配布に未対応で、利用者ごとのApp設定が必要。Chatworkのトークンも本人が用意する。LINEはGrok Botのブラウザ操作に依存し、実MCPの送受信と既読影響をまだ検証していない。
- 公開側のIP単位のアクセス制限、監視、障害通知、メールによる招待・パスワード再設定は未実装。
