# 再レビューと実装判断

初回: 2026-10-18、更新: 2026-10-19

## 修正した問題

| 指摘 | 修正 |
|---|---|
| 利用者IDだけでは会話と連携先の取り違えをDBが拒否できない | `COMMANDS(conversation_id, connection_id, user_id)` に複合外部キー |
| 送信リース切れ後に再配布するとLINEが二重送信し得る | `uncertain` へ移し自動再配布しない |
| クリック成功を「送信済み」と誤表示し得る | `executing` 後、宛先と送信後表示の確認が報告されたときだけ `sent` |
| 再配信・連打で重複登録し得る | イベントキー、外部メッセージID、リクエストIDの一意制約。会話の未確定送信中は追加送信も拒否 |
| 他人のLINE操作を一つのBotに集約するとログインが混ざる | 利用者別のLINEブリッジ鍵を1連携に紐付け、鍵の再発行で旧鍵を失効 |
| LINEブリッジの設計がHTTPだけでGrok Botに接続しにくい | Streamable HTTPの `/mcp` を追加 |
| ER図と実装テーブルが異なる | 11テーブルの実装スキーマに図を更新 |
| 共通公開時に利用者がAPIトークンを手入力する設計だった | 招待制の本人別ログインと期限付きセッションを追加。既存トークンは移行用に残す |
| 会話と本文を全件返すと人数・履歴の増加で応答が重くなる | 会話・本文を50件単位で取得し、利用者別の件数上限を設けた |
| 稼働中DBのコピーは復旧できない可能性がある | SQLiteバックアップAPIと整合性確認を使う手順を追加し、復元テストを実施 |

## 現時点で残る問題

- Grok BotでLINEを操作できることは利用者の再現実績として扱う。2026-10-18に別の一時HTTPS MCPで `inbox_probe` の実行を確認した。Bearer必須に変更した後も、試験サーバーに認証済みの `tools/call inbox_probe` が記録された。この受信箱の `/mcp` への接続とLINEを含む実データの一往復は未実施。
- 2026-10-19に検証用Bot「MCP接続テスト」へ個人LINEのログイン状態だけを確認させたが、このBot環境ではChrome版LINEの拡張機能が見つからず、`web.line.me` も接続エラーだった。利用者が再現したBot環境との違いを特定する必要がある。会話本文・連絡先の読み取りと送信は行っていない。
- LINEの宛先同定と送信後確認は画面操作の観測に依存する。サーバーはBotの自己報告を検証できない。
- Chatwork Webhookの失敗時は再送されない。定期履歴照合を追加したが、取得上限（直近100件）を超えると欠落の可能性を表示する。DM/メンションへ絞り込む。
- Teamsのチャット別購読作成・更新と資格情報の手動更新を追加した。OAuthによる自動トークン更新と実資格情報によるAPI送信は未検証。
- Slackの現Webhook URLは連携ごとに異なり、共有Slack Appによる複数利用者のOAuth接続に未対応。Slack通知の履歴照合も未実装。
- 単一サーバー用のDocker Compose、HTTPS設定、認証試行制限、バックアップ手順を追加したが、実サーバーでの起動と復旧訓練は未実施。保持期間、公開側のIP単位レート制限、永続ジョブ処理も未実装。
- Gmailの本人端末エージェントとMessengerのブラウザブリッジを追加した。資格情報を作成者に預けない条件として新規セットアップは所有者一人のインスタンスに制限する。Gmail API、Google OAuth、Messengerブラウザを実アカウントで接続していない。既存の共有サーバー運用は[資格情報の保管と配布](credential-custody.md)の条件を満たさない。

以上のため、この実装は本人所有インスタンスを既定とする検証版として扱う。各人への配布判断には上の残件の解消と実アカウントでの確認が必要。
